---
title: Architecture
description: How a save in your editor becomes a checkpoint in someone else's browser tab.
---

biga is three programs and a database: a CLI that watches a folder, a server
that stores what the CLI sends and relays it, and a viewer that renders it.
Nothing is pushed from the server to your machine, and the viewer never talks
to the CLI.

## The whole system

```mermaid title="The whole system" summary="Your folder is read by the biga CLI on your machine. The CLI uploads over HTTP to the server's REST API, which writes to Postgres and, optionally, publishes events through Redis. The server streams events to viewers' browsers, which read state and file content over the same API." caption="Your folder goes in one side and a browser tab comes out the other. Redis is optional and only matters with more than one server."
flowchart TB
  folder["<b>Your folder</b><br/>.gitignore · .bigaignore"] --> cli["<b>biga CLI</b><br/>watch · hash · batch"]
  cli -- "protobuf · gzip" --> api

  subgraph host["Server · Go"]
    api["<b>REST API</b><br/>uploads and reads"]
    sse["<b>Live stream</b><br/>live events"]
  end

  api -- "in-process" --> sse
  api --> db[("<b>Postgres</b><br/>source of truth")]
  api -. "publish" .-> redis[("<b>Redis</b> · optional<br/>events · cache")]
  redis -. "other instances" .-> sse
  sse -- "checkpoint events" --> viewer["<b>Viewer</b><br/>any browser"]
  viewer -- "GET state · file" --> api
```

- **The CLI** is one Go binary. It is the only thing that ever reads your files.
- **The server** is one Go binary. It accepts uploads over REST and delivers
  live events over a streaming protobuf response. See the [HTTP API](/docs/api). The
  site and viewer are a separate Next.js app that holds no data.
- **Postgres** is the source of truth for every session. **Redis** is optional
  and only needed to run more than one server instance.
- **The viewer** is the page a link opens. It loads a session's state once and
  then follows a stream.

There are no accounts anywhere. The session ID is the credential to watch,
which is why the CLI is careful about [what it shares](/docs/what-gets-shared).
Writing needs more: the owner token the server issued when the session was
created, and an access key if the server requires one.

## What the CLI does between a save and an upload

```mermaid title="What the CLI does between a save and an upload" summary="Six stages in order: watch for changed paths, filter them through the ignore rules, batch them until the folder is quiet, read and hash the files, diff against the last synced hashes, then upload the difference. If nothing differs, nothing is sent." caption="The watcher only says a path may have changed. Content hashes decide what actually did, which keeps it right across editors that write in place, rename over, or delete and recreate."
flowchart TB
  W["<b>1 · Watch</b> — fsnotify, 75 ms to settle"] --> F["<b>2 · Filter</b> — built-ins, .gitignore, .bigaignore"]
  F --> B["<b>3 · Batch</b> — 120 ms quiet, or 1 s into a burst"]
  B --> R["<b>4 · Read</b> — skip binary and over 2 MB, SHA-256"]
  R --> D{"<b>5 · Diff</b> — hash changed?"}
  D -- "yes" --> U["<b>6 · Upload</b> — gzip, under 6 MB, buffered offline"]
  D -- "no" --> N(["nothing sent"])
```

Three details are worth knowing:

- **A burst is one checkpoint.** Every change restarts a quiet timer
  (`BIGA_IDLE_MS`, 120 ms). A long burst is cut at `BIGA_MAX_WAIT_MS` (1 s) so
  viewers never wait on you for long. Flushes run one at a time, in order, so
  uploads never overlap or reorder.
- **Hashes decide, not events.** A path the watcher reports is re-read and
  hashed, and only a different hash becomes a change. Saving a file without
  changing it sends nothing.
- **An ignore file is a change too.** Editing a `.gitignore` or `.bigaignore`
  re-checks every synced file and rescans the tree, so newly ignored files
  disappear for viewers and newly included ones appear.

## One save, end to end

```mermaid title="One save, end to end" summary="The editor writes a file and the CLI sees a filesystem event. After the folder has been quiet for 120 milliseconds, or one second into a burst, the CLI re-reads the paths, hashes them and diffs. It posts a gzip checkpoint, the server answers 202, assigns a sequence number, writes blobs and moves the head, then sends a checkpoint event to the viewer. The viewer updates its tree and timeline and fetches a file's content by hash only when it is opened." caption="Only changed files travel, and only after the folder has been quiet. A save that doesn't change a file's hash sends nothing."
sequenceDiagram
  autonumber
  participant E as Your editor
  participant C as biga CLI
  participant S as Server
  participant V as Viewer
  E->>C: file written (fsnotify event)
  Note over C: quiet for 120 ms, or 1 s into a burst
  C->>C: re-read paths, SHA-256, diff
  C->>S: POST /checkpoint (gzip)
  S-->>C: 202 accepted
  S->>S: assign seq, write blobs, move head
  S-)V: event: checkpoint
  V->>V: update tree and timeline
  V->>S: GET /file?path&ref=hash
  S-->>V: content, cached by hash
```

The upload is answered with `202` as soon as it is accepted. The server assigns
the checkpoint a sequence number that is monotonic per session, writes the
content it hasn't seen before, moves the head of the tree, and then publishes
the event. A viewer applies the event to its tree and timeline, and fetches a
file's content only when someone opens it.

## Starting and rejoining

A new session uploads a full snapshot first, then streams changes. The snapshot
is sent in two steps so a large project never has to fit in one request: the file
content goes first, in batches, and the snapshot that follows carries only
hashes.

```mermaid title="Starting a new session" summary="The CLI creates the session with a PUT, arms the file watcher, scans the folder and uploads a full snapshot. The server stores the tree and blobs. When a viewer opens the link it loads the state and then opens the event stream, which answers with a connected event." caption="The watcher is armed before the tree is read, so an edit made during the first upload is queued, not lost."
sequenceDiagram
  participant C as biga CLI
  participant S as Server
  participant V as Viewer
  C->>S: PUT /sessions/:id
  Note over C: arm the file watcher, then scan the folder
  C->>S: POST /blobs/missing, POST /blobs
  C->>S: POST /snapshot (hashes only)
  S->>S: store tree, seq 0
  rect rgba(120, 120, 120, 0.12)
    Note over V,S: a viewer opens the link
    V->>S: GET /state
    S-->>V: session, checkpoints, tree
    V->>S: GET /stream
    S-)V: event: connected
  end
```

Running `biga start` again in the same folder finds the session ID saved for
it and **rejoins**. Local files are always the source of truth, so the CLI
asks the server for its manifest, uploads only the difference, and the link
never changes.

```mermaid title="Rejoining a session" summary="The CLI reactivates the session with a PUT, asks the server for its manifest of paths, hashes and sizes, and diffs its local tree against it. It posts a checkpoint with only the changed files, and the server sends a checkpoint event to viewers. If nothing differs, nothing is uploaded." caption="Local files are the source of truth. The CLI asks what the server has, uploads the difference, and the link never changes."
sequenceDiagram
  participant C as biga CLI
  participant S as Server
  participant V as Viewer
  C->>S: PUT /sessions/:id
  Note over C,S: session reactivated, same link
  C->>S: GET /manifest
  S-->>C: path, hash, size per file
  C->>C: diff the local tree against it
  alt files differ
    C->>S: POST /checkpoint (changed only)
    S-)V: event: checkpoint
  else already in sync
    Note over C: nothing to upload
  end
```

If the manifest isn't available (an older server), the CLI falls back to a full
snapshot. Changes made while the server cannot be reached are buffered and
sent when it comes back.

## Live delivery

A viewer holds one `GET /api/sessions/:id/stream` open. The server writes these
frames on it:

| Event | When |
| --- | --- |
| `connected` | First, when the stream opens. |
| `checkpoint` | A checkpoint was accepted. Carries the changes. |
| `snapshot` | The whole tree was replaced. |
| `session_ended` | The broadcast stopped, or went quiet for too long. |
| `keepalive` | Every 15 seconds, so an idle connection stays open. |

Each frame is a protobuf message preceded by its length. Viewers only receive,
so a streaming HTTP response is enough: ordinary HTTP, with no second channel
to keep open. The viewer reads the stream itself rather
than leaving reconnection to the browser, so it can see why a connection was
refused and wait as long as the server asks. When a stream drops, the viewer
reconnects saying where it left off, and the server sends what it missed. [How the viewer handles
this](#how-the-viewer-applies-events) is covered below.

A broadcast that stops sending heartbeats is marked ended once its session has
been quiet for 45 seconds, so a laptop that died doesn't look live forever.
The CLI sends a heartbeat every 10 seconds, and skips one when a checkpoint
was just sent, since the server counts that as a sign of life too.

### How the viewer applies events

The viewer treats the stream as a source of facts about the tree, never as
text. A `checkpoint` event says which paths changed and their new hashes, and a
file's content is fetched by hash only when someone opens it. That keeps a busy
broadcast from costing more than the part of it on screen.

```mermaid title="Inside the viewer" summary="The browser reads the event stream with fetch. Each event is validated, then ordered by sequence number, with duplicates dropped and gaps detected. Pending changes are merged into one batch, and only one batch is in flight at a time. The batch is applied once per animation frame to the tree and timeline stores, which the tree, timeline and editor read. When a file is opened, its content is fetched by hash and cached." caption="Everything before the stores runs off the main thread when the browser allows it. A slow page gets fewer, larger batches instead of a growing queue."
flowchart LR
  stream["<b>Event stream</b><br/>GET /stream"] --> decode["<b>Validate</b><br/>drop malformed events"]
  decode --> order["<b>Order</b><br/>duplicates · gaps"]
  order --> merge["<b>Merge</b><br/>one batch in flight"]
  merge -- "once per frame" --> stores["<b>Stores</b><br/>tree · timeline"]
  stores --> ui["<b>Tree · timeline · editor</b>"]
  ui -. "a file is opened" .-> cache["<b>Content cache</b><br/>by hash"]
  cache -- "GET file" --> api["<b>REST API</b>"]
```

- **Validation.** Every event is checked against its schema before it is used.
  Three bad events in a row make the viewer re-read the state instead of
  guessing.
- **Ordering.** Events carry a sequence number. Duplicates are dropped, and a
  gap makes the viewer re-read the state. While it does, new events wait and
  are replayed afterwards. If more than 48 pile up, it stops replaying and
  re-reads instead, well before the server would drop a slow reader at 64.
- **Merging.** Changes that arrive close together are combined: a file saved
  five times is one update with its last hash, and a file added then deleted
  is no update at all. The next batch is held until the page has applied the
  last one, with at least 50 ms between them.
- **Large sessions.** Building the tree for 50,000 files is split into slices
  across animation frames and published in one step, so the page stays
  responsive while it loads.
- **Content.** Files are cached by hash, so a version seen once is not fetched
  again. Hovering or focusing a file for a moment fetches it ahead of time, and
  the browser's own cache keeps any hash-addressed file for a year.

#### When the connection drops

| What happens | What the viewer does |
| --- | --- |
| The stream closes or errors | Shows **Reconnecting**, keeps the last state on screen, and retries after a delay that starts at one second, grows to 30, and is randomised so viewers don't retry together. |
| The server answers 429 or 503 | Waits for the `Retry-After` it was given. |
| Nothing arrives for 45 seconds | Treats the stream as dead and reconnects. The server sends a keepalive frame every 15 seconds, so this means three missed in a row. |
| It reconnects | Opens the stream saying which checkpoint and snapshot it holds. If the server can replay what it missed, it applies those in order. Otherwise it re-reads the state first. |
| Eight attempts in a row fail | Shows **Offline** with a reconnect button. The browser coming back online also tries again. |
| The tab was hidden for 30 seconds | Lets go of the stream, so a forgotten tab does not hold a connection. When it is visible again it reconnects and catches up the same way. |
| `session_ended` arrives | Shows the final state and stops reconnecting. |

### More than one server

Events are delivered to the viewers connected to the instance that received
the checkpoint first, and then published to Redis for the others. Each
instance stamps what it publishes and ignores its own echo, so nothing is
delivered twice. Without `REDIS_URL` everything stays in the process.

<Callout type="warn" title="Needs a long-running host">
Holding a stream open for every viewer means the server has to be a
long-running process. A purely serverless or edge deployment can't fan live
events out.
</Callout>

## The data model

```mermaid title="The data model" summary="A session has one snapshot of the current tree, many checkpoints, many head files and many blobs. A checkpoint has many changes, and changes and head files both point at blobs by hash." caption="Content is stored once, by hash, per session. A checkpoint is metadata that points at blobs, so re-saving a file to an earlier state costs nothing."
erDiagram
  sessions ||--o| snapshots : "current tree"
  sessions ||--o{ checkpoints : "history"
  sessions ||--o{ files : "head"
  sessions ||--o{ blobs : "content"
  checkpoints ||--o{ checkpoint_changes : "contains"
  checkpoint_changes }o--o| blobs : "before, after"
  files }o--|| blobs : "points at"

  sessions {
    text id PK
    text status "active or ended"
    bytea owner_token_hash "SHA-256"
  }
  snapshots {
    jsonb tree "metadata only"
  }
  checkpoints {
    int seq "monotonic"
    text label
  }
  checkpoint_changes {
    text path
    text change_type
  }
  files {
    text path PK
    text hash
  }
  blobs {
    text hash PK
    bytea content "raw or brotli"
  }
```

- **Content is addressed by hash.** Each unique `(session, sha-256)` is stored
  once, as raw UTF-8 or brotli, and referenced by hash from the tree, the head
  files and every checkpoint change. `hash` and `size` always describe the raw
  bytes, so the encoding is invisible to callers.
- **Binary files are recorded, not stored.** They get a row with `binary` set
  and no bytes.
- **An upload is one transaction.** The checkpoint, its changes, new blobs and
  the moved head commit together with the session row locked, so writers to a
  session take turns and a viewer never sees half an upload.
- **A session cascades.** Deleting a session deletes everything under it, which
  is what the retention sweep relies on.

### Eager and lazy loading

When a viewer opens a small session the server sends every current file's
content with the state, so files open instantly. A session over roughly
1.5 MB or 400 files is served lazily instead: the state carries the tree, and
content is fetched per file, by hash, as it is opened. Both thresholds are
[configurable](https://github.com/biga-app/server#limits-and-tuning).

## Properties worth relying on

| Property | Why it holds |
| --- | --- |
| A crash is repaired by running the same command | Local files are the source of truth, and rejoin diffs against the server. |
| Unchanged files are never re-sent | Uploads are keyed by SHA-256, and a file whose hash hasn't changed isn't uploaded again. |
| Only the broadcaster writes | Every write needs the session's owner token, which only the creating CLI holds. |
| History is complete | Checkpoints are append-only, and content is immutable by hash. |
